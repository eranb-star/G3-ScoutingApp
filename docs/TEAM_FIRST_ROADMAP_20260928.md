## User clarification — practical learning design
- VR already exists. Do not recreate it. Proposed phase 5 means additional training missions, comparison and coaching on the shared delivered web/phone/VR engine. Preserve controller mapping/deadman, views, fullscreen, physics independent of graphics tier, scoring/inventory and replay; test affected paths and distinguish desktop from headset acceptance.
- Robot configuration means a versioned setup record, not mandatory video: selected robot, physical versus simulated run, code revision when known, relevant mechanism/settings, battery/test conditions and date. Reuse existing settings; manually enter physical values until integration exists. Unknown values remain unknown. Snapshot each test so later edits do not rewrite historical comparisons. Photo/video is optional evidence, never proof of hidden electrical/mechanical quality.
- Proposed visual workshop learning: reuse Skills Academy and real CAD viewer, add curated manufacturer-specific component/port models and annotated real photos, then constrained drag/drop placement, wiring diagrams and assembly exercises. Start with one published reference electronics board and one intake assembly. Approved/attributed imagery and licensed CAD must be sourced; generic generated imagery cannot establish exact connectors/wiring. Real team overlay awaits photos/CAD/components list. Device/pin/spec/rule versions must be explicit. Deterministic known-connection checks can assess a virtual layout; images/CAD alone cannot certify crimp quality, termination, secure mounting, torque, heat or competition reliability. Provide physical checks and qualified review. Placement has tradeoffs, not one universally correct location. CAN is a routed communication bus, not a box to place.
- Mechanical examples: exploded assemblies, part selection/order, shafts/bearings/spacers/retention, tube/gusset/fastener connections, belt/chain alignment and service access. Annotated authored scenes are feasible; arbitrary CAD-to-correct-step-by-step assembly generation is not an initial promise. Structural/fastener specifications require the actual component/material/load data and source guidance.
- WPILib desktop code simulation is separate from the delivered browser physics simulator. Integrate the existing robot project/build/simulation tools when repository access exists; do not rebuild WPILib or claim the current web twin executes team robot code. Remote execution needs a bounded isolated worker/local companion, not arbitrary uploaded-code execution in the browser.
- Logging: begin one declared format (e.g. WPILib .wpilog) once real samples exist; map available signals/units/time to robot version, inspect synchronized plots/events, compare target versus observed behavior, and attach timestamped findings. Not all useful signals are automatically logged; absent data stays absent. Simulator telemetry is synthetic and separately labelled. DS logs/video are separate formats, not silently supported by a .wpilog importer.
- Prebuilt bilingual curriculum is a proposed deliverable, not only a course editor. Initial bounded pack: six modules (power/component identification; CAN/sensors; wiring/mounting inspection; mechanical fastening; shafts/bearings/transmission; intake/shooter testing), each with visual lessons, ten questions and two practical assignments. English/Hebrew share item IDs/rubric/answer keys/source revision; localized feedback and RTL; protect assessment answers from student access. Deterministic objective scoring; evidence-based human review for physical practical qualification. Read/quiz completion is not permission to operate machinery. Start approved content without widening paid AI permissions or monthly budget.
These clarifications refine the proposed roadmap; no new feature implementation is started by this discussion.
